## 0. How to use this document (read this first)

You are implementing a backend + frontend system in **strict phase order**: Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4 → Phase 5 → Phase 6a → 6b → 6c.

**Rules you must follow:**

1. **Do not start a phase until the previous phase's Exit Criteria are all met and passing.** Each phase has a checklist — treat it as a gate, not a suggestion.
2. **Do not build anything listed under a phase's "Explicitly NOT in this phase" section**, even if it seems like a natural extension. It is deferred on purpose. Building it early creates integration risk with later phases that assume a simpler starting point.
3. **Tech stack choices in this document are final decisions, not options.** Do not substitute a different library, framework, or pattern because you judge it "better" — if you believe a listed choice is actually wrong, stop and flag it in your output rather than silently swapping it.
4. **Every schema, endpoint path, table name, and file path in this document is exact and must be used verbatim.** Do not invent additional endpoints, rename fields, or restructure the repo layout unless a phase explicitly tells you to.
5. **If you are not certain of a library's exact function signature, current package name, or current API shape, say so explicitly in your output instead of guessing.** Do not fabricate a plausible-looking function call. This project has already been through one review cycle that caught fabricated-looking assumptions (see §1) — don't reintroduce them.
6. **Commit at the end of each phase**, with a commit message referencing the phase number and version tag (e.g. `Phase 1 complete — v0.2: deterministic ingestion`).
7. **Write and run tests before declaring a phase done.** A phase without a passing test for its exit criteria is not complete.
8. Ask before deviating. If a requirement in this doc conflicts with something you observe while building (e.g., a library was deprecated, a package renamed), pause and surface the conflict instead of resolving it silently.

## 1. Fixed tech stack (final — do not substitute)

| Layer | Locked choice | Notes |
|---|---|---|
| Language / runtime | Python 3.11+ | Backend only. Frontend is separate (Node/TypeScript). |
| API framework | **FastAPI** | Async-native. Use `async def` routes only where the handler body is actually async (see §7). |
| ORM / migrations | **SQLModel** + **Alembic** | SQLModel model classes double as Pydantic schemas where reasonable. Review autogenerated Alembic migrations by hand — do not trust them blindly. |
| Database | **PostgreSQL 15** | Relational; findings/corrections/rules are joined data. |
| Data validation | **Pydantic v2** | Single schema source of truth across DB models, LLM structured output, and API request/response bodies. |
| Deterministic CLI parsing | **TextFSM** + **`ntc-templates`** (`ntc_templates.parse.parse_output`) | Do not hand-write regex parsers for vendors that already have an ntc-templates entry. `parse_output(platform, command, data)` requires an *exact* platform string and an *exact* command string match — the raw text passed in must contain only the command's output, not the command line itself. |
| LLM fallback | **Anthropic API**, model string **`claude-opus-5`**, via **`instructor`** (`instructor.from_anthropic(...)`) | Use the **async** client `anthropic.AsyncAnthropic()` wrapped by `instructor.from_anthropic()`, and `await` all calls from `async def` routes. Never call a synchronous Anthropic client from inside an `async def` route — it blocks the event loop. If cost/latency becomes a problem later, `claude-sonnet-5` is the pre-approved downgrade — do not swap in any other model without flagging it. |
| Background jobs | **FastAPI `BackgroundTasks`** + `asyncio.gather` for intra-batch concurrency (v1.0). **Celery + Redis is Phase 6 only** — do not introduce a message broker before then. |
| Rule engine | **Bespoke YAML rule packs + a pure-Python evaluator** (v1.0). **Open Policy Agent / Rego is Phase 6 only.** |
| PDF reporting | **WeasyPrint** rendering a **Jinja2** HTML template with `autoescape=True` | Requires system packages `libpango-1.0-0 libpangocairo-1.0-0 libcairo2 libgdk-pixbuf2.0-0 libffi-dev shared-mime-info` installed in the Docker image — this is a common silent build failure, install them explicitly in the Dockerfile. |
| Frontend | **React + Vite + TypeScript + Tailwind CSS** | Three screens only for v1.0: Upload, Findings Dashboard, Training. No Next.js, no SSR. |
| Containerization | **Docker Compose** (`api`, `db`, `frontend` services) | |
| Testing | **pytest**, using `ntc-templates`' own bundled test fixtures as parser regression data (see §10 of the LLD / Phase 1 below) | |

**Do not introduce, at any point in v1.0:** Celery, Redis, OPA/Rego, `pgvector`, authentication/RBAC, Netmiko/NAPALM live-device polling, a second LLM provider, or a local/self-hosted LLM. All of these are named, scoped, and scheduled for Phase 6 — see §9.

## 3. Fixed data models (Pydantic v2 — `app/models/schema.py`)

Use these exact field names and types. Do not rename or drop fields — later phases depend on this exact shape.

```python
from pydantic import BaseModel, Field
from typing import Literal
from datetime import datetime

class SourceEvidence(BaseModel):
    raw_line: str
    line_number: int | None = None

class SecurityBaselineField(BaseModel):
    control_area: str
    value: str
    evidence: SourceEvidence
    confidence: float = Field(ge=0.0, le=1.0)
    source_lane: Literal["deterministic", "llm"]

class DeviceIdentity(BaseModel):
    hostname: str | None = None
    serial_number: str | None = None
    model: str | None = None
    firmware_version: str | None = None

class NormalizedDeviceConfig(BaseModel):
    device_id: str
    vendor: str
    os_hint: str | None = None
    identity: DeviceIdentity = DeviceIdentity()
    fields: list[SecurityBaselineField]
    parsed_at: datetime

class ComplianceRule(BaseModel):
    control_id: str
    framework: Literal["CIS", "NIST_800_53", "STIG", "ISO_27001"]
    control_area: str
    expected_value: str
    severity: Literal["low", "medium", "high", "critical"]
    remediation_template: str

class Finding(BaseModel):
    device_id: str
    control_id: str
    status: Literal["pass", "fail", "needs_review"]
    observed_value: str | None
    severity: str
    remediation_cli: str | None
    evidence: SourceEvidence | None

class CorrectionExample(BaseModel):
    vendor: str
    os_hint: str | None
    raw_line: str
    mapped_control_area: str
    mapped_value: str
    corrected_by: str
    created_at: datetime
```

## 4. Fixed database schema (`app/models/tables.py` → Alembic migration)

```sql
CREATE TABLE devices (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    filename TEXT NOT NULL,
    vendor TEXT,
    os_hint TEXT,
    detection_confidence FLOAT,
    hostname TEXT,
    serial_number TEXT,
    model TEXT,
    firmware_version TEXT,
    raw_config TEXT NOT NULL,
    uploaded_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE normalized_fields (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id UUID REFERENCES devices(id) ON DELETE CASCADE,
    control_area TEXT NOT NULL,
    value TEXT NOT NULL,
    raw_line TEXT NOT NULL,
    confidence FLOAT NOT NULL,
    source_lane TEXT NOT NULL CHECK (source_lane IN ('deterministic','llm')),
    superseded BOOLEAN NOT NULL DEFAULT false,
    updated_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_normalized_fields_device_active
    ON normalized_fields (device_id, control_area) WHERE NOT superseded;

CREATE TABLE compliance_rules (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    control_id TEXT NOT NULL,
    framework TEXT NOT NULL,
    control_area TEXT NOT NULL,
    expected_value TEXT NOT NULL,
    severity TEXT NOT NULL,
    remediation_template TEXT
);

CREATE TABLE findings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id UUID REFERENCES devices(id) ON DELETE CASCADE,
    control_id TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('pass','fail','needs_review')),
    observed_value TEXT,
    severity TEXT,
    remediation_cli TEXT,
    raw_line TEXT,
    evaluated_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE corrections (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor TEXT NOT NULL,
    os_hint TEXT,
    raw_line TEXT NOT NULL,
    mapped_control_area TEXT NOT NULL,
    mapped_value TEXT NOT NULL,
    corrected_by TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_corrections_vendor_os ON corrections (vendor, os_hint);
```

Build this table set fully in **Phase 0**, including the device-identity columns, even though they aren't populated until later phases. Retrofitting columns after the report template exists is more expensive than including them up front.

## 6. Anti-hallucination guardrails specific to this project

These are known failure points from the design review — do not repeat them:

- **`re.MULTILINE` is required** on every fingerprint regex in `vendor_detect.py` that uses `^` as an anchor. Without it, `^` only matches position 0 of the entire string, not the start of each line.
- **`parse_output()` needs both `platform` AND `command` to match exactly.** A vendor fingerprint alone is not enough — you must also decide which `command` string the uploaded config corresponds to (assume `"show running-config"` for Cisco IOS-family full-config uploads unless told otherwise) and verify a template exists for that exact `(platform, command)` pair before calling it.
- **Wrap every `parse_output()` call in try/except**, and treat both a raised exception AND an empty return value as "no deterministic match" — route to the LLM fallback lane in both cases, don't just handle the exception case.
- **Never send raw, unredacted config text to the Anthropic API.** Always call `redact()` (Phase 4) first.
- **Never call a synchronous Anthropic/instructor client from an `async def` FastAPI route.** Use `AsyncAnthropic` and `await`, or make the route a plain `def` so FastAPI threadpools it.
- **The model string is `claude-opus-5`.** Do not invent a different model string (e.g. do not use `claude-sonnet-4-6`, `claude-3-opus`, or any other string that isn't `claude-opus-5` or the approved fallback `claude-sonnet-5`).
- **Jinja2 template for the PDF must have `autoescape=True`** — config lines and remediation CLI often contain `<`/`>` (ACL syntax) which will break unescaped HTML.
- **CORS middleware must explicitly allow the frontend origin** (`http://localhost:5173` in dev) or all frontend→backend calls fail silently in the browser with no useful backend-side error.
- **A correction submitted via `/training/corrections` must trigger re-evaluation** of every device whose fields it affects — not just re-normalization. If this loop doesn't close, the findings dashboard will not visibly update after a correction, which defeats the purpose of the training module.

## 8. Phase 1 — Unified Ingestion Engine + Deterministic Normalization
**Version tag: v0.2 · Difficulty: Low–Medium · Covers PS Deliverable #1 + Dev Workflow Stage 1**

**Build:**
- `app/ingestion/vendor_detect.py`: multi-keyword scored fingerprinting (see §6 for the `re.MULTILINE` requirement), returning `vendor`, `os_hint`, `confidence`, `ntc_platform`, `assumed_command`.
- `app/parsers/deterministic.py`: `parse_deterministic(platform, command, raw_text)` wrapping `ntc_templates.parse.parse_output`, raising a custom `NoDeterministicTemplate` exception on failure or empty result (per §6 guardrail).
- `app/api/devices.py`: `POST /devices/upload` (accept single file or list of files, store `raw_config` + `filename`, run vendor detection, return `device_id`(s)); `GET /devices`; `GET /devices/{id}`.
- `app/api/parse.py`: `POST /devices/{id}/parse` — runs the deterministic parser only in this phase (no LLM fallback yet — if it fails, store the device with a `needs_llm_fallback` status/flag you define now for Phase 4 to pick up, don't error out to the user).
- `GET /devices/{id}/fields` returning stored `normalized_fields`.
- `frontend/src/pages/Upload.tsx`: file picker (single + multi-select), upload button, list of uploaded devices with detected vendor + confidence.
- Add `ntc-templates`' own bundled test fixtures to `backend/tests/fixtures/` — pull real Cisco IOS and Juniper Junos sample outputs from the `ntc-templates` GitHub repo's `tests/` directory structure (e.g. `tests/cisco_ios/show_run/`) to use as both pytest regression inputs and demo data.
- `pytest` tests: upload a known-vendor fixture, assert vendor detection confidence, assert `parse_deterministic()` returns non-empty structured data with `confidence == 1.0` fields.

**Explicitly NOT in this phase:** LLM fallback, rule evaluation, PDF reports, training UI, Palo Alto/Fortinet/SONiC/any vendor without an ntc-templates match (those come back as `needs_llm_fallback` and stop there).

**Exit criteria:**
- Uploading a Cisco IOS or Juniper Junos fixture through the API returns structured, normalized fields with `source_lane="deterministic"` and `confidence=1.0`.
- Bulk upload (2+ files in one request) works.
- pytest suite passes on the fixture-based regression tests.

## 9. Phase 2 — Multi-Framework Compliance Engine
**Version tag: v0.3 · Difficulty: Medium · Covers PS Deliverable #3 + Dev Workflow Stage 2**

**Build:**
- `app/rules/packs/*.yaml`: at minimum 3–4 real rules per framework to start (CIS SSH version, CIS telnet disabled, NIST password policy, STIG logging requirement) — expand later, don't try to encode entire benchmarks yet.
- `app/rules/engine.py`: `evaluate(fields, rules) -> list[Finding]`. A rule with no matching field, or a field below the confidence threshold (define `CONFIDENCE_THRESHOLD = 0.75` as a settings constant now, even though nothing routes below it yet in this phase), must produce `status="needs_review"` — never silently skip a rule.
- `app/api/frameworks.py`: `GET /frameworks` returning the fixed list `["CIS", "NIST_800_53", "STIG", "ISO_27001"]`.
- `app/api/findings.py`: `POST /devices/{id}/evaluate?framework=CIS` (writes to `findings` table) and `GET /devices/{id}/findings`.

**Explicitly NOT in this phase:** LLM-sourced fields (nothing is below the confidence threshold yet since Phase 1 only produces `confidence=1.0` fields), a findings dashboard UI beyond a simple table (that's fine for now, doesn't need polish yet), PDF export.

**Exit criteria:**
- For a Phase-1 fixture device, running `/evaluate?framework=CIS` produces a mix of `pass`/`fail` findings matching your hand-written rule pack, persisted in the `findings` table.
- `GET /devices/{id}/findings` returns them correctly.

## 11. Phase 4 — AI/LLM Fallback Lane
**Version tag: v0.5 · Difficulty: High · Covers Dev Workflow Stage 3, begins PS Deliverable #5**

This is the first phase with genuine AI risk. Read §6's guardrails again before starting.

**Build:**
- `app/ingestion/redact.py`: regex-based redaction of secret-hash lines, PSKs, SNMP community strings, and generic `api_key=...` patterns — run on any text before it is sent to the Anthropic API.
- `app/parsers/llm_fallback.py`: `async def parse_with_llm(vendor, raw_config, few_shot=None) -> NormalizedDeviceConfig`, using `instructor.from_anthropic(AsyncAnthropic())`, `model="claude-opus-5"`, `response_model=NormalizedDeviceConfig`, prompting the model to cite the exact source line and set an honest confidence per field.
- Update `app/api/parse.py`'s `/devices/{id}/parse`: if `parse_deterministic()` raises `NoDeterministicTemplate` (covers both "no template exists" and "template exists but returned nothing"), call `await parse_with_llm(...)` instead, store fields with `source_lane="llm"` and their real per-field confidence.
- For bulk uploads specifically: use `asyncio.gather()` across devices that need the LLM lane so they parse concurrently, not sequentially.
- Add Palo Alto (`iron-skillet` repo `set`-format samples) and FortiOS (`config`-block samples) fixtures to `backend/tests/fixtures/` as the "known vendor, no deterministic template" test case for this phase.

**Explicitly NOT in this phase:** the training UI, few-shot retrieval from real corrections (pass `few_shot=None` for now — that wiring is Phase 5), any change to the rule engine's confidence-threshold behavior beyond what Phase 2 already built.

**Exit criteria:**
- Uploading a Palo Alto or FortiOS fixture routes automatically to the LLM lane (confirm via `source_lane="llm"` in the stored fields) and produces fields with real confidence scores, not all identical placeholder values.
- Confirm via logs or a test double that the raw config sent to the LLM has been redacted first.
- Confirm the parse call does not block other concurrent requests (a simple concurrency test: fire two uploads needing LLM fallback at once, confirm they don't serialize).

## 12. Phase 5 — AI-Powered Training Module
**Version tag: v1.0 · Difficulty: Highest · Completes PS Deliverable #2, completes PS Deliverable #5**

**All 5 PS deliverables are present after this phase — this is the v1.0 milestone.**

**Build:**
- `app/training/corrections.py`:
  - `get_few_shot_examples(vendor, os_hint, limit=5)` — pull the most recent matching corrections.
  - `submit_correction(correction: CorrectionExample)` — insert into `corrections`, mark the old `normalized_fields` row `superseded=true` rather than deleting it (preserve audit trail), write the corrected value, **then re-run `evaluate()` for every device whose `(vendor, os_hint, control_area)` this correction affects** — this is the guardrail from §6, do not skip it.
- Wire `few_shot` into `parse_with_llm()`: before calling the LLM for a given vendor, fetch `get_few_shot_examples()` and inject them into the prompt.
- `app/api/training.py`: `GET /training/pending` (all fields with `confidence < CONFIDENCE_THRESHOLD` across all devices, joined with their raw line and device vendor for context), `POST /training/corrections`.
- `frontend/src/pages/Training.tsx`: list of pending low-confidence fields, each showing the raw source line, a text input to map it to a `control_area` and `value`, submit button calling `POST /training/corrections`.
- `frontend/src/pages/Findings.tsx`: findings dashboard, must reflect `needs_review` findings flipping to `pass`/`fail` after a correction is submitted (poll or refetch after submission — don't require a manual page state reset).
- Add SONiC (`config_db.json`) and MikroTik (`.rsc` export) fixtures as the "genuinely unrecognized format" test case — neither resembles any Cisco/Juniper structure, so these are honest tests of the full loop rather than a relabeled Phase 4 case.

**Explicitly NOT in this phase:** `pgvector`-based semantic few-shot retrieval (the keyed `(vendor, os_hint)` lookup is sufficient for v1.0), authentication on who can submit a correction (`corrected_by` can be a free-text field for now), bulk/batch correction submission UI.

**Exit criteria:**
- Upload a SONiC or MikroTik fixture → confirm several fields land in `GET /training/pending`.
- Submit a correction for one of those fields → confirm the corresponding `finding` for that device flips from `needs_review` to `pass`/`fail` without any manual re-trigger.
- Upload a **second, different** SONiC/MikroTik fixture from the same vendor family → confirm the previously-corrected `control_area` now comes back from the LLM lane with confidence above the threshold, unassisted, because the few-shot example was injected.

## 14. Definition of done for the whole project

The project is v1.0-complete when, without any manual intervention beyond what the UI provides:
1. A user can upload a single file or multiple files of any of the vendor types listed in this document's fixtures.
2. Known-vendor files parse deterministically; known-vendor-but-untemplated files parse via LLM; genuinely unknown files land in the training queue.
3. A user can select a framework (CIS/NIST/STIG/ISO) and get pass/fail findings with severity.
4. A user can download a single PDF per device containing device identification, findings, and remediation CLI.
5. A user can correct a low-confidence field once, and the system applies that correction to that device's findings immediately, and to future uploads of the same vendor automatically.
