1. Tech stack — the decisions, and why

Layer Choice Why this and not the obvious alternative
API / orchestrator Python 3.11 + FastAPI Async-native, auto-generates OpenAPI (useful for the frontend and for judges), and it's the only ecosystem where the parsing libraries, the LLM tooling, and the network-automation libraries all live together without a language bridge.
Deterministic parsing TextFSM + `ntc-templates` (via ntc_templates.parse.parse_output) This is a real, widely-used, actively maintained library (Network to Code) purpose-built for exactly this problem — turning vendor CLI output into structured data via community-maintained templates. Don't hand-roll regex parsing when this exists.
Live device pulls (optional) Netmiko (wraps Paramiko, has built-in use_textfsm=True to call ntc-templates directly) Named in the brief; battle-tested for SSH automation across 50+ platforms.
LLM fallback Anthropic or OpenAI API + `instructor` + Pydantic v2 instructor patches the API client so the model is forced to return a validated Pydantic object instead of free text you then have to regex out. This is what makes confidence scoring and source-line citation structural instead of hopeful.
Data validation / schema Pydantic v2 Same schema definitions double as the normalized data model, the LLM's structured output contract, and the API's request/response models — one source of truth, not three.
Database PostgreSQL 15 Relational because findings, corrections, and few-shot examples are all joined by device/vendor/OS-version — this is not document-shaped data.
ORM / migrations SQLModel (FastAPI author's own library, Pydantic + SQLAlchemy in one) + Alembic for migrations Keeps the Pydantic models and the DB models from drifting into two parallel schemas you maintain by hand.
Few-shot / correction retrieval Postgres + `pgvector` extension (optional upgrade) or a plain (vendor, os_hint) keyed lookup for the hackathon cut Start with the keyed lookup — it's simpler and demoable. pgvector is the natural v2 if you want similarity-based retrieval across less exact matches.
Background jobs FastAPI `BackgroundTasks` for hackathon scale; Celery + Redis if you outgrow it Bulk upload of tens of files doesn't need a broker. Don't add infrastructure you can't demo the value of.
Rule packs YAML files, loaded at startup, hot-reloadable Rules are data, not code — this is the actual point of the architecture, so don't undermine it by putting rules in Python.
PDF report WeasyPrint (HTML/CSS → PDF) Faster to make look professional than ReportLab's imperative canvas API under time pressure; you design the report as an HTML template.
Frontend React + Vite + TypeScript + Tailwind Three screens (upload, findings dashboard, training/correction UI) — no need for Next.js routing/SSR complexity.
Testing pytest + `ntc-templates'` own test fixtures as parser regression tests See §10 — this doubles as your dummy data source.
Containerization Docker Compose (api, worker if used, postgres, frontend) One command to stand the whole thing up for a demo.

4. Core data models (Pydantic v2)

These live in models/schema.py and are reused as: the LLM's forced structured-output contract, the normalized storage shape, and the API response shape.

from pydantic import BaseModel, Field
from typing import Literal
from datetime import datetime

class SourceEvidence(BaseModel):
    raw_line: str                       # the exact original config line
    line_number: int | None = None

class SecurityBaselineField(BaseModel):
    control_area: str                   # e.g. "ssh_version", "telnet_enabled", "password_min_length"
    value: str                          # the normalized value, e.g. "2", "false", "8"
    evidence: SourceEvidence
    confidence: float = Field(ge=0.0, le=1.0)   # 1.0 for deterministic-lane fields
    source_lane: Literal["deterministic", "llm"]

class NormalizedDeviceConfig(BaseModel):
    device_id: str
    vendor: str
    os_hint: str | None = None
    fields: list[SecurityBaselineField]
    parsed_at: datetime

class ComplianceRule(BaseModel):
    control_id: str                     # e.g. "CIS-1.1.4"
    framework: Literal["CIS", "NIST_800_53", "STIG", "ISO_27001"]
    control_area: str                   # must match a SecurityBaselineField.control_area
    expected_value: str
    severity: Literal["low", "medium", "high", "critical"]
    remediation_template: str           # e.g. "ip ssh version 2" — vendor-specific fill-in

class Finding(BaseModel):
    device_id: str
    control_id: str
    status: Literal["pass", "fail", "needs_review"]
    observed_value: str | None
    severity: str
    remediation_cli: str | None
    evidence: SourceEvidence | None

class CorrectionExample(BaseModel):
    vendor: str
    os_hint: str | None
    raw_line: str
    mapped_control_area: str
    mapped_value: str
    corrected_by: str
    created_at: datetime

5. Database schema (Postgres DDL, via SQLModel/Alembic)

CREATE TABLE devices (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    filename TEXT NOT NULL,
    vendor TEXT,
    os_hint TEXT,
    detection_confidence FLOAT,
    raw_config TEXT NOT NULL,
    uploaded_at TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE normalized_fields (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id UUID REFERENCES devices(id) ON DELETE CASCADE,
    control_area TEXT NOT NULL,
    value TEXT NOT NULL,
    raw_line TEXT NOT NULL,
    confidence FLOAT NOT NULL,
    source_lane TEXT NOT NULL CHECK (source_lane IN ('deterministic','llm'))
);

CREATE TABLE compliance_rules (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    control_id TEXT NOT NULL,
    framework TEXT NOT NULL,
    control_area TEXT NOT NULL,
    expected_value TEXT NOT NULL,
    severity TEXT NOT NULL,
    remediation_template TEXT
);

CREATE TABLE findings (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    device_id UUID REFERENCES devices(id) ON DELETE CASCADE,
    control_id TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('pass','fail','needs_review')),
    observed_value TEXT,
    severity TEXT,
    remediation_cli TEXT,
    raw_line TEXT
);

CREATE TABLE corrections (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    vendor TEXT NOT NULL,
    os_hint TEXT,
    raw_line TEXT NOT NULL,
    mapped_control_area TEXT NOT NULL,
    mapped_value TEXT NOT NULL,
    corrected_by TEXT,
    created_at TIMESTAMPTZ DEFAULT now()
);
CREATE INDEX idx_corrections_vendor_os ON corrections (vendor, os_hint);

6. API contract

Method Endpoint Purpose
POST /devices/upload Upload one or more config files. Returns device_id(s).
GET /devices/{id} Device metadata, detected vendor, detection confidence.
POST /devices/{id}/parse Triggers vendor detection → deterministic or LLM lane → normalization.
GET /devices/{id}/fields Returns normalized fields with confidence + evidence.
POST /devices/{id}/evaluate?framework=CIS Runs the rule engine, writes findings.
GET /devices/{id}/findings Returns findings for the dashboard.
GET /devices/{id}/report.pdf Generates and streams the PDF report.
GET /training/pending Lists low-confidence fields awaiting human review, across all devices.
POST /training/corrections Submits a human correction; writes to corrections, triggers re-normalization of affected fields.

7. Module-by-module design

7.1 Vendor detection (ingestion/vendor_detect.py)

Pure Python, no AI — this needs to be fast and cheap since it runs on every upload before any real parsing happens.

FINGERPRINTS = [
    ("cisco_ios", r"^Building configuration|^version \d+\.\d+\nservice"),
    ("juniper_junos", r"^## Last commit:|^system \{"),
    ("panos", r"<config version=|^set (deviceconfig|network|rulebase)"),
    ("fortios", r"^config (system|firewall) "),
    ("sonic", r'"DEVICE_METADATA"\s*:\s*\{'),          # config_db.json signature
    ("mikrotik_routeros", r"^/interface|^/ip address\nadd"),
]
# score each pattern, return (vendor, os_hint, confidence)
# confidence >= TEMPLATE_THRESHOLD and a matching ntc-templates index entry
# → deterministic lane. Otherwise → LLM fallback lane.

7.2 Deterministic parser (parsers/deterministic.py)

from ntc_templates.parse import parse_output

def parse_deterministic(vendor_platform: str, command: str, raw_text: str):
    # vendor_platform must match ntc-templates' platform naming,
    # e.g. "cisco_ios", "juniper_junos"
    return parse_output(platform=vendor_platform, command=command, data=raw_text)

Every value coming out of this path gets confidence = 1.0 and source_lane = "deterministic" — there's no ambiguity to score.

7.3 LLM fallback lane (parsers/llm_fallback.py)

import instructor
from anthropic import Anthropic
from app.models.schema import NormalizedDeviceConfig

client = instructor.from_anthropic(Anthropic())

def parse_with_llm(vendor: str, raw_config: str) -> NormalizedDeviceConfig:
    return client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4000,
        response_model=NormalizedDeviceConfig,
        messages=[{
            "role": "user",
            "content": (
                f"Vendor: {vendor}\n"
                "Extract every security-relevant setting from this config into the schema. "
                "For every field, quote the EXACT source line you derived it from, and set "
                "confidence honestly — if you are guessing, say so with a low number.\n\n"
                f"{raw_config}"
            ),
        }],
    )

Key design point: response_model makes the schema itself the contract — the model literally cannot return something that doesn't have evidence.raw_line and confidence populated. This is what turns "trust me" into something checkable.

A field routes to the Training UI when confidence < CONFIDENCE_THRESHOLD (start at 0.75, tune from real usage).

7.4 Training UI backend (training/corrections.py)

def get_few_shot_examples(vendor: str, os_hint: str | None, limit: int = 5):
    # simple keyed lookup for the hackathon cut:
    return db.exec(
        select(Correction)
        .where(Correction.vendor == vendor, Correction.os_hint == os_hint)
        .order_by(Correction.created_at.desc())
        .limit(limit)
    ).all()

These examples get formatted into the LLM prompt as few-shot context on the next call for that vendor — this is the entire "training loop," and it's a prompt-construction problem, not a model-retraining problem.

7.5 Rule engine (rules/engine.py)

# rules/packs/cis_ios.yaml
- control_id: CIS-1.1.4
  framework: CIS
  control_area: ssh_version
  expected_value: "2"
  severity: high
  remediation_template: "ip ssh version 2"
- control_id: CIS-1.2.1
  framework: CIS
  control_area: telnet_enabled
  expected_value: "false"
  severity: critical
  remediation_template: "no service telnet"
def evaluate(fields: list[SecurityBaselineField], rules: list[ComplianceRule]) -> list[Finding]:
    field_map = {f.control_area: f for f in fields}
    findings = []
    for rule in rules:
        field = field_map.get(rule.control_area)
        if field is None:
            findings.append(Finding(status="needs_review", ...))  # never silently skip
        elif field.confidence < CONFIDENCE_THRESHOLD:
            findings.append(Finding(status="needs_review", ...))
        else:
            status = "pass" if field.value == rule.expected_value else "fail"
            findings.append(Finding(status=status, remediation_cli=rule.remediation_template, ...))
    return findings

7.6 Reporting (reporting/generate.py)

Jinja2 renders templates/report.html with the device metadata + findings list, then weasyprint.HTML(string=rendered).write_pdf(...).

8. Sequence flow per lane

Deterministic (Cisco/Juniper):

POST /devices/upload → vendor_detect fingerprints as cisco_ios with high confidence → parse_deterministic() via ntc-templates → fields written with confidence=1.0 → POST /devices/{id}/evaluate runs rule engine → GET /report.pdf.

LLM fallback (Palo Alto, no template):

Upload → vendor_detect recognizes vendor name but has no ntc-templates match → parse_with_llm() called with no few-shot examples (first time) → fields returned with per-field confidence → all fields ≥ 0.75 → straight to rule engine → report. No human touches this run.

LLM fallback + training (unknown SONiC device):

Upload → vendor_detect returns low confidence, os_hint=None → parse_with_llm() called → several fields return confidence < 0.75 → those fields appear in GET /training/pending → human calls POST /training/corrections for each → correction stored → next SONiC upload calls get_few_shot_examples() first and injects them into the prompt → confidence on those same fields should now clear the threshold automatically.

10. Dummy data — real sources, 2–3 examples per lane

Rather than hand-writing fake configs from scratch, pull from the actual repositories these vendors/communities publish — the data is realistic, free, and in some cases is literally what the parsing library's own tests run against.

Lane 1 — Purely deterministic (Cisco / Juniper, has an ntc-templates match)

Best source: the ntc-templates repo's own test fixtures — real, anonymized show run / show version outputs used to test the exact library you're integrating.

🔗 https://github.com/networktocode/ntc-templates/tree/master/tests — browse tests/cisco_ios/show_run/ and tests/juniper_junos/

Ready-to-use example 1 — Cisco IOS (minimal show run fragment):

Building configuration...

hostname EDGE-SW01
!
service password-encryption
!
line vty 0 4
 transport input ssh
!
ip ssh version 2
no service telnet
!
username admin privilege 15 secret 5 $1$abc$XyZ...

Ready-to-use example 2 — Juniper Junos (set-style):

system {
    host-name CORE-FW01;

            protocol-version v2;

Lane 2 — LLM fallback (known vendor, no deterministic template)

Best source: PaloAltoNetworks/iron-skillet — Palo Alto's own official GitHub repo of ready-to-load NGFW configs in both XML and set-command format.

🔗 https://github.com/PaloAltoNetworks/iron-skillet → loadable_configs/

Ready-to-use example 1 — Palo Alto (set format fragment):

set rulebase security rules allow-outbound source any destination any application any action allow log-end yes

Ready-to-use example 2 — FortiOS (config block fragment):

    set admin-ssh-v1 disable
    set admintimeout 15

Lane 3 — Human review + LLM fallback (genuinely unrecognized format)

Best source: SONiC's own config_db.json schema documentation and sample configs, straight from the sonic-net/sonic-buildimage repo — a format almost nothing has a hand-built parser for.

🔗 https://github.com/sonic-net/sonic-buildimage — see src/sonic-yang-models/doc/Configuration.md and src/sonic-config-engine/config_samples.py (ships t1/l2/empty preset sample configs)

🔗 https://github.com/sonic-net/SONiC/wiki/Configuration

Ready-to-use example 1 — SONiC config_db.json fragment:

{
    "DEVICE_METADATA": {
        "localhost": {
            "hostname": "sonic-tor01",
            "hwsku": "Accton-AS7326-56X"
        }
    },
    "BGP_NEIGHBOR": {
        "10.0.0.1": {
            "admin_status": "up",
            "asn": "65100",
            "name": "T1-01"
        }
    }
}

Ready-to-use example 2 — MikroTik RouterOS export (.rsc), an equally good "never seen it" case:

🔗 official export docs: https://help.mikrotik.com/docs/spaces/ROS/pages/328155/Configuration+Management

/interface bridge
add name=bridge1
/ip address
add address=10.1.0.1/24 interface=bridge1
/ip service
set telnet disabled=yes
set ssh port=22

Why these two work well as lane-3 examples: neither SONiC's JSON key-value schema nor MikroTik's /path + add/set syntax resembles any Cisco/Juniper template structure at all — a deterministic parser genuinely has nothing to match against, so these are honest tests of the full fallback-plus-training loop, not just a relabeled lane-2 case.

Quick-start order

  1. Stand up Postgres + FastAPI skeleton, wire the devices upload endpoint.
  2. Drop lane-1 fixtures in, get ntc_templates.parse_output returning real structured data.
  3. Hand-write 3–4 compliance_rules YAML entries and get pass/fail working end to end on lane 1 only — this proves the whole spine before AI enters the picture.
  4. Add the LLM fallback lane with instructor + the Pydantic schema, test against lane-2 fixtures.
  5. Add the confidence threshold gate and the corrections table, test against lane-3 fixtures.
  6. Wire the PDF report last — it's the least risky part and easiest to leave for the end.
